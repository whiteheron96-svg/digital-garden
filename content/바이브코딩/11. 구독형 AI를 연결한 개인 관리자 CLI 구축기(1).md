# 구독형 Claude와 Codex를 한 명령으로: 개인용 멀티 에이전트 관리자 CLI 구축기

AI 코딩 도구를 여러 개 구독하고 있어도 실제 작업은 의외로 번거롭다. Claude에게 계획을
물어보고, 그 계획을 Codex에 옮겨 적고, 테스트를 실행하고, 결과를 검토한 뒤 Git에
반영하는 과정을 사람이 계속 이어줘야 한다.

이번에는 이 연결 작업을 담당하는 작은 개인용 관리자 CLI를 만들었다. 목표는 거대한 AI
플랫폼을 한 번에 만드는 것이 아니었다. 터미널에서 `ai`라고 입력하면 Claude와 Codex가
정해진 역할을 수행하고, 원본은 사용자가 승인할 때까지 보호되는 최소한의 자동화부터
시작했다.

## 처음 생각했던 큰 그림

출발점은 사용하지 않는 MacBook을 24시간 개인 AI 개발 서버로 활용하는 구상이었다.

```text
관리용 노트북
    │
    ├─ SSH / Tailscale
    │
    ▼
24시간 서버
├─ Claude Code
├─ Codex CLI
├─ 작업 관리자
├─ PostgreSQL
├─ Redis
├─ Dashboard
├─ Slack
└─ 로컬 모델
```

하지만 PostgreSQL, Redis, Docker와 대시보드부터 만들기 시작하면 정작 중요한
“AI 작업 한 건이 처음부터 끝까지 제대로 흐르는가?”를 늦게 확인하게 된다. 그래서 첫
목표를 다음 한 줄로 줄였다.

> Claude가 계획하고, Codex가 구현하고, 테스트 결과를 기록하는 작업 한 건을 완주한다.

## 역할을 고정하니 사용법이 단순해졌다

범용 멀티 에이전트 도구는 사용자가 모델과 작업 공간, 세션을 직접 선택할 수 있다. 반면
개인용 도구에서는 역할을 미리 정해도 된다.

```text
사용자 요청
    ↓
Claude Code: 저장소 분석과 계획
    ↓
Codex CLI: 코드 작성과 수정
    ↓
프로젝트 테스트
    ↓
사용자 검토와 승인
```

사용자는 에이전트를 하나씩 열 필요가 없다. 프로젝트 폴더에서 자연어로 명령한다.

```bash
ai 로그인 화면을 만들고 테스트도 추가해줘
```

조금 더 안내가 필요하면 `ai`만 입력한다.

```bash
ai
```

그러면 할 일, 프로젝트, 테스트 명령을 차례로 물어본다. `package.json`, pytest 설정,
`Cargo.toml`, `go.mod`, Makefile 등이 있으면 테스트 명령도 자동으로 제안한다.

## Git은 GitHub가 아니라 안전장치였다

이 도구는 Git 저장소가 필요하다. 여기서 Git 저장소는 반드시 GitHub에 공개되는
저장소를 뜻하지 않는다. `git init`은 로컬 컴퓨터에 변경 이력을 만들 뿐이고, 별도로
push하지 않으면 인터넷에 올라가지 않는다.

Git을 요구한 이유는 worktree 때문이다. 작업을 시작하면 현재 커밋에서 별도 브랜치와
worktree를 만든다.

```text
원본 프로젝트 (HEAD)
├─ 사용자가 작업하는 폴더
└─ AI 전용 worktree
   ├─ Claude 계획
   ├─ Codex 변경
   └─ 테스트 결과
```

Claude, Codex와 테스트 명령은 모두 AI 전용 worktree 안에서 실행된다. 원본에
커밋되지 않은 변경은 복사하지 않으며, AI 결과도 승인 전에는 원본에 나타나지 않는다.

작업 후에는 짧은 명령만 기억하면 된다.

```bash
ai 상태
ai 결과
ai 변경
ai 승인
ai 취소
```

- `ai 상태`: 현재 진행 단계와 테스트 상태를 본다.
- `ai 결과`: Codex의 최종 요약을 본다.
- `ai 변경`: 원본에 반영될 diff를 확인한다.
- `ai 승인`: 변경을 로컬 커밋으로 원본에 반영한다.
- `ai 취소`: 격리 변경과 작업 브랜치를 폐기한다.

승인은 GitHub push를 수행하지 않는다. 원본 저장소가 깨끗할 때만 작업 브랜치의 커밋을
원본에 적용하고, 충돌이 생기면 cherry-pick을 중단하고 원상복구한다.

## CLI를 자동 실행하면 무조건 API 요금일까?

구축 과정에서 가장 헷갈렸던 부분이다. 결론부터 말하면 CLI를 자동으로 실행한다는 사실과
API 종량제 과금은 같은 의미가 아니다. 어떤 방식으로 로그인했는지가 중요하다.

Codex는 ChatGPT 계정으로 로그인하면 ChatGPT 플랜의 사용량과 크레딧 정책을 따르고,
API 키로 로그인하면 API 표준 요금이 적용된다. 자세한 구분은
[OpenAI Codex 인증 문서](https://learn.chatgpt.com/docs/auth)에서 확인할 수 있다.

Claude Code 역시 Claude 구독 계정과 API 키 인증을 구분한다. 다만 이 관리자에서
사용하는 `claude -p` 비대화형 실행은 2026년 6월부터 별도의 Agent SDK 자동화
크레딧 정책이 적용된다. 정책은 바뀔 수 있으므로
[Anthropic의 안내](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)를
확인해야 한다.

예상치 못한 종량제 사용을 막기 위해 관리자는 실행 전에 다음을 검사한다.

```text
Codex가 ChatGPT 계정으로 로그인했는가?
Claude가 유료 claude.ai 계정으로 로그인했는가?
CODEX_API_KEY가 설정되어 있지 않은가?
OPENAI_API_KEY가 설정되어 있지 않은가?
ANTHROPIC_API_KEY가 설정되어 있지 않은가?
```

하나라도 통과하지 못하면 worktree를 만들기 전에 중단한다. 검사 후 자식 프로세스에도
세 API 키 환경 변수를 전달하지 않는다. 상태 확인은 다음 한 줄이면 된다.

```bash
ai doctor
```

Claude 계정의 추가 사용량 크레딧 활성화 여부는 로컬 CLI에서 확인할 수 없었다. 추가
과금을 완전히 막으려면 Claude의 Settings → Usage에서 사용량 크레딧을 직접 꺼야 한다.

## 실패한 테스트를 Codex가 다시 고치게 만들기

첫 버전은 테스트가 한 번 실패하면 작업 전체를 실패로 끝냈다. 하지만 구현 오류를
발견하기 위해 테스트를 실행했다면, 실패 로그를 구현 에이전트에게 다시 주는 것이 자연스럽다.

현재 흐름은 다음과 같다.

```text
Codex 구현
    ↓
테스트 실행
    ↓ 실패
실패 로그 마지막 부분 추출
    ↓
Codex 자동 수정
    ↓
테스트 재실행
    ├─ 성공 → 작업 완료
    └─ 실패 → 허용 횟수 확인
```

기본 자동 수정은 1회다. 고급 명령에서는 0회부터 최대 3회까지 지정할 수 있다.

```bash
admin-ai run "로그인 오류 수정" \
  --repo /path/to/project \
  --test-command "python -m pytest" \
  --retries 2
```

재시도 횟수를 제한한 이유는 명확하다. 같은 실패를 이해하지 못한 채 무한 반복하면
코드 품질이 좋아지기보다 변경 범위와 구독 사용량만 커질 수 있다. 자동 수정 프롬프트에도
테스트 삭제나 완화로 실패를 숨기지 말고, 사용자 요청 범위 안에서 원인을 최소한으로
수정하라고 명시했다.

각 시도는 별도 파일로 남는다.

```text
test-attempt-1.log
codex-repair-1.log
repair-1.md
test-attempt-2.log
```

따라서 최종 테스트가 통과해도 첫 실패 원인과 Codex가 어떤 판단으로 수정했는지 다시
확인할 수 있다.

## 실제 스모크 테스트에서 확인한 것

임시 로컬 Git 저장소를 만들고 README 한 줄을 수정하는 작업으로 전체 흐름을 시험했다.

```text
작업 접수
→ 격리 공간 준비
→ Claude 계획
→ Codex 구현
→ 테스트
→ 성공
```

원본 저장소에는 변경이 없었고, AI 전용 worktree에만 README 변경이 생겼다. 작업 상태,
계획, Codex 로그, 테스트 로그와 결과 요약도 모두 작업 디렉터리에 저장됐다. 자동 수정
기능을 추가한 뒤에는 모의 테스트로 첫 실패 후 성공하는 경우와 허용 횟수를 모두 사용한
뒤 실패하는 경우를 각각 검증했다. 현재 자동화 테스트는 21개다.

## Orca와 Antigravity가 있는데 왜 직접 만들었을까?

[Orca](https://www.onorca.dev/)는 Claude Code, Codex 등 여러 CLI 에이전트를 worktree에서
나란히 실행하고, 에디터·브라우저·모바일·diff 검토까지 제공한다. 여러 에이전트를 동시에
운용할 때는 이번 개인 CLI보다 훨씬 풍부하다.

[Google Antigravity](https://developers.googleblog.com/en/build-with-google-antigravity-our-new-agentic-development-platform/)는
IDE, 터미널과 브라우저를 오가며 에이전트가 계획·구현·검증하고 Artifact를 통해 결과를
보여주는 완성형 플랫폼에 가깝다.

직접 만든 도구의 목적은 이 제품들을 기능 수로 이기는 것이 아니다. 다음과 같은 개인
규칙을 가장 작은 인터페이스로 고정하는 데 있다.

```text
Claude는 계획한다.
Codex는 구현하고 실패를 수정한다.
모든 작업은 격리한다.
API 키가 있으면 실행하지 않는다.
사용자가 승인하기 전에는 원본에 반영하지 않는다.
GitHub에는 자동으로 올리지 않는다.
```

Orca는 병렬 에이전트 운영에, Antigravity는 IDE와 브라우저를 포함한 시각적 작업에 더
적합하다. 이번 CLI는 개인 프로젝트에서 복잡한 설정 없이 `ai 할 일`로 정해진 협업
절차를 실행하는 데 초점을 맞췄다.

## 개인정보와 로컬 Git

로컬 Git에 개인 문서를 저장한다고 자동으로 인터넷에 공개되는 것은 아니다. 하지만
파일을 삭제해도 과거 커밋에 남을 수 있고, 백업이나 동기화로 복제되거나 나중에 실수로
원격 저장소에 push할 수 있다. 이 관리자는 worktree에도 파일을 복제하고 AI가 저장소를
읽게 하므로 API 키, 비밀번호, 인증 토큰, 개인 키와 고위험 개인정보는 `.gitignore`로
제외하는 편이 안전하다.

## 지금 가능한 것과 다음 목표

현재 가능한 기능은 다음과 같다.

- `ai` 대화형 실행과 최근 프로젝트 선택
- `ai 할 일` 자연어 단축 명령
- Claude 계획 → Codex 구현 → 테스트
- 테스트 실패 시 제한된 자동 수정과 재시험
- Git worktree 격리
- 구독 전용 인증 점검
- 최근 작업의 상태·결과·diff 확인
- 승인 또는 취소
- 모든 단계의 로그와 작업 상태 저장

아직 없는 기능도 있다.

- Claude의 최종 코드 리뷰
- 여러 작업의 병렬 큐
- 백그라운드 실행과 알림
- 원격 서버 운영
- 웹 대시보드

다음 단계는 Codex의 자동 수정으로 테스트가 통과한 뒤 Claude가 diff를 최종 검토하고,
중대한 문제가 없을 때만 사용자에게 승인을 요청하는 흐름이다. 그 다음에야 백그라운드
큐와 Slack 알림을 붙일 계획이다.

## 마치며

멀티 에이전트 시스템이라고 해서 처음부터 데이터베이스, 큐와 대시보드가 필요한 것은
아니었다. 가장 먼저 필요했던 것은 역할, 격리, 검증, 승인이라는 네 가지 경계였다.

작은 CLI로 시작하니 실제로 어떤 자동화가 유용하고 어디에서 사람이 개입해야 하는지가
더 분명해졌다. 지금 기억해야 할 사용법은 여전히 짧다.

```bash
ai 할 일
ai 결과
ai 변경
ai 승인  # 또는 ai 취소
```

자동화의 목표는 사람을 완전히 없애는 것이 아니라, 반복적인 연결 작업은 기계에 맡기고
최종 판단은 사람이 더 쉽게 내릴 수 있도록 만드는 것이었다.
