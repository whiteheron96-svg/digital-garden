# 브라우저 콘솔로 공공데이터 긁기 삽질기

> 60개 농가의 토양검정 데이터를 손으로 53번 조회하다 지쳐서, 브라우저에게 대신 시킨 이야기. 그리고 그 과정에서 배운 세 가지 함정.

## 발단: 손으로 53번은 못 하겠다

과수의 당도 산도에 영향을 주는 환경변수 중 **토양**이 제일 중요하다는 선행연구가 있었다. 토양 데이터는 농촌진흥청 **흙토람**(soil.rda.go.kr)에서 필지별로 조회할 수 있다. 로그인도 필요 없다. 좋다.

문제는 **필지가 53개**라는 것. 한 필지 조회하려면:

1. 시/도 → 제주 선택
2. 시/군 → 서귀포시 선택 *(→ 읍면동 목록 로딩)*
3. 읍/면/동 → 남원읍 선택 *(→ 리 목록 로딩)*
4. 리 → 남원리 선택 *(→ 검정 필지 목록 뜸)*
5. 목록에서 내 지번(295) 클릭
6. 검정일자 선택 → 조회
7. 화면에 뜬 pH·유기물·유효인산… 숫자 옮겨적기

이걸 53번. 드롭다운 클릭만 최소 300번이다. 노가다도 이런 노가다가 없다.

그래서 생각했다. **이 클릭을 코드가 대신하면 안 되나?**

## 개념: "웹페이지도 결국 조작 가능한 객체다"

우리가 보는 웹페이지는 브라우저 안에서 **DOM(Document Object Model)**이라는 객체 트리로 존재한다. 드롭다운도, 버튼도, 표에 찍힌 숫자도 전부 자바스크립트로 접근·조작할 수 있는 객체다.

그리고 모든 브라우저에는 **개발자도구 콘솔(F12 → Console)**이 있다. 여기에 자바스크립트를 입력하면 **지금 열려 있는 페이지의 문맥에서 즉시 실행**된다. 즉, 콘솔은 "이 페이지를 마음대로 주무를 수 있는 리모컨"이다.

그래서 자동화의 본질은 단순하다:

> **사람이 마우스로 하는 ①~⑦을, 콘솔에서 자바스크립트로 그대로 재현한다.**

- 드롭다운 선택 → `select.value = "130"` 후 페이지의 로딩 함수 호출
- 목록에서 필지 찾기 → 옵션 텍스트를 정규식으로 매칭
- 표의 숫자 읽기 → `table.innerText`에서 숫자만 추출
- 53번 반복 → `for` 반복문
- 결과 저장 → CSV 텍스트를 만들어 브라우저 다운로드

별도 프로그램 설치도, 서버도, API 키도 없다. **브라우저 하나로 끝난다.** 이게 콘솔 스크래핑의 매력이다.

## 그런데 여기서부터 삽질이 시작된다

개념은 5분이면 이해하는데, 실제로 돌리면 온갖 곳에서 터진다. 내가 부딪힌 세 가지를 공유한다. 셋 다 "자동화가 사람보다 빨라서" 생기는 문제라는 게 재밌다.

### 함정 1. 레이스 컨디션 — "로딩 끝나기 전에 다음을 눌러버린다"

시/군을 선택하면 읍/면/동 목록이 **서버에서 비동기(AJAX)로** 채워진다. 사람은 목록이 뜰 때까지 눈으로 기다렸다가 다음을 누른다. 그런데 코드는 눈이 없다. 선택하자마자 0.001초 뒤에 다음 드롭다운을 건드린다. 아직 안 채워진 목록에서 "남원읍"을 찾으니 당연히 없다. → 실패.

처음엔 "옵션이 생길 때까지 기다리기(polling)"로 해결하려 했다. 그런데 더 교묘한 버그가 있었다. **이전 그룹의 낡은 옵션이 그대로 남아 있어서**, 기다림 조건이 즉시 통과해버린 것. 결국 53필지 전부 실패로 돌았다(진행률만 올라가서 한참 몰랐다).

**교훈:** 비동기 로딩 뒤엔 "그냥 기다리기"보다 **"값이 실제로 바뀌었는지 확인"**이 안전하다. 나는 결국 각 단계 뒤 고정 2.2초 대기 + 재시도 2회로 못을 박았다. 우아하진 않아도 확실하다.

### 함정 2. 낡은 DOM — "화면은 그대로인데 나는 다음 걸 읽는다"

필지 A를 조회하면 표에 A의 값이 뜬다. 이어서 필지 B를 조회하는데, B의 표가 렌더링되기 전에 코드가 표를 읽으면 **A의 값을 B의 값인 줄 알고 가져간다.**

실제로 겪었다. 서로 다른 두 필지가 **소수점까지 완전히 똑같은 값**(pH 4.3, 유기물 147, 유효인산 580…)으로 나왔다. 통계에서 이런 우연은 없다. 낡은 값을 읽은 거였다.

**교훈:** 화면을 다시 그리는 작업 뒤엔 "이전 값과 달라졌는지"를 확인하거나, 아예 **페이지를 새로고침해서 낡은 흔적을 지우고** 시작하는 게 가장 확실하다. 나는 후자를 택했다.

### 함정 3. 실행시간 제한 — "한 번에 다 하려다 강제 종료"

원격으로 브라우저를 조작하는 도구에는 보통 **한 명령당 시간 제한**(내 경우 45초)이 있었다. 53필지를 한 번에 돌리는 함수는 몇 분이 걸리니 당연히 중간에 잘렸다. 심지어 무거운 렌더링이 겹치면서 페이지 자체가 **프리즈**되기도 했다.

**교훈:** 두 가지 방법이 있다.
- **작게 쪼개기** — 몇 개씩 나눠 여러 번 호출
- **분리 실행** — 스크립트를 페이지 안에 띄워놓고(제어권을 넘기고), 나는 진행률만 가끔 확인

그리고 결정적으로, **"내가 원격으로 조작"하는 것보다 "사용자가 자기 브라우저 콘솔에서 직접 실행"하는 게 훨씬 안정적**이었다. 원격 제어와 페이지의 무거운 동작이 충돌하지 않기 때문이다. 그래서 최종본은 **콘솔에 붙여넣어 직접 돌리는 스크립트**로 정리했다.

## 안전과 매너

콘솔에 코드를 붙여넣으면 크롬이 **"allow pasting을 입력하라"**며 막는다. 겁주는 게 아니라 진짜 방어장치다 — 남이 준 코드를 무심코 붙여넣으면 그 페이지의 내 세션(로그인·개인정보)까지 코드가 만질 수 있으니까. 그래서 원칙은 하나다:

> **내가 이해하지 못한 코드는 붙여넣지 않는다.**

내가 만든 스크립트는 (1) 흙토람 페이지 안에서만 돌고, (2) 공개된 조회 기능만 사람처럼 클릭하며, (3) 결과를 **내 컴퓨터에 CSV로만** 저장한다. 외부 전송도, 로그인도, 설치도 없다. 그리고 매너로 각 조회 사이에 약간의 간격을 둬서 서버를 두들기지 않게 했다.

## 언제 이걸 쓰고, 언제 쓰지 말아야 하나

사실 **공식 API가 있으면 API가 정답**이다. 흙토람도 오픈API가 있다. 그런데 이번엔 API를 안 썼다. 이유가 재밌다:

- **API는 법정동(읍·면·동) 단위 평균값**만 준다.
- 내 연구는 **필지별 차이**가 핵심인데, 평균을 쓰면 남원읍 23개 농가가 전부 똑같은 pH가 되어버린다.
- 정작 **필지별 실측값은 웹 조회 화면에만** 있었다.

그래서 "API가 있어도 내가 원하는 입도(粒度)의 데이터가 없으면, 화면 스크래핑이 유일한 길"이 되기도 한다. 이번이 딱 그 경우였다.

정리하면:

| 상황 | 방법 |
|------|------|
| 공식 API가 원하는 데이터를 준다 | **API 사용** (1순위) |
| API는 있는데 입도/항목이 부족하다 | 화면 스크래핑 검토 |
| 로그인·개인정보가 걸린 데이터 | 자동화 금지, 직접 조회 |
| 반복이 수십 번 이상 & 공개 데이터 | 콘솔 스크립트가 가성비 최고 |

## 마치며

결국 "브라우저 콘솔 자동화"는 거창한 기술이 아니라 **사람의 반복 클릭을 코드가 대신하는 것**이다. 개념은 쉬운데, 실전은 "코드가 사람보다 빨라서 생기는" 타이밍 문제와의 싸움이었다. 레이스 컨디션, 낡은 DOM, 시간 제한 — 이 셋만 알고 가도 절반은 먹고 들어간다.

그리고 가장 큰 교훈: **완벽한 자동화보다, 멈춰도 이어서 할 수 있게 만드는 게 더 실용적이다.** 그래서 최종본엔 "이미 조회한 필지는 건너뛰고 이어하기" 기능을 넣었다. 5분짜리 작업이 중간에 멈춰도 처음부터 다시 안 해도 되게.

노가다 53번을, 붙여넣기 한 번으로. 그게 이번 삽질의 결론이다.
